Part 1 · covers "Agent Skills with Anthropic" + "Introduction to Agent Skills"

The skill-authoring skills 7 min live

There are skills whose whole job is building other skills. Two carry this session: anthropic-skills:skill-creator scaffolds, edits, and evals a skill and tunes its description so it triggers accurately, and superpowers:writing-skills supplies the authoring discipline - tight, testable, one job per skill. Learn these two and skill-writing stops being guesswork.

Liveskill-creator - scaffold, edit, eval, tune2 min▶

anthropic-skills:skill-creator is the workhorse. Point it at a job and it creates the folder, writes a starter SKILL.md with front matter, and - the part people skip - runs an eval on the description to check triggering accuracy.

  • Create - scaffolds the skill folder and a first-draft body from your description of the job.
  • Edit - improves an existing skill without you hand-editing markdown.
  • Eval - tests that the skill fires on tasks that should match and stays quiet on those that shouldn't.
  • Tune the description - the single highest-leverage edit, because the description is all Claude reads to decide whether to open the skill.
★ Try it nowUse skill-creator to scaffold a skill for a job I repeat: [name the job in one line]. Draft the description, then tell me what phrasing would and wouldn't trigger it.
Why the eval matters A skill that never fires is worse than no skill - it's dead weight you forget you own. The eval catches a too-narrow or too-vague description before you ship, when it's cheap to fix.
Livewriting-skills - the authoring discipline2 min▶

superpowers:writing-skills is less a tool than a set of rules for what a good skill looks like. It exists because the easy failure mode is a bloated skill that tries to do five jobs and triggers on none of them clearly.

  • One job - a skill does a single thing well. Two jobs means two skills.
  • Tight - the body is instructions, not an essay. Depth goes in reference files, not the always-scanned part.
  • Testable - you can state plainly what "working" means, so you can eval it.
Real world

An early draft of a data skill tried to cover profiling, charting, and a scorecard in one body. It triggered inconsistently and the body was huge. Split into three single-job skills with sharp descriptions, each fired reliably and each body dropped to under a screen. Same coverage, far cleaner triggering, fewer tokens.

Self-studyThe description is the whole trigger2 min read▶

This is worth internalizing before you write a line. Claude decides whether to open your skill from the name and description alone - the body is invisible until that decision is made. So the description does two jobs at once:

  • It is the trigger - pack it with the words a matching task would actually contain ("use when the user wants to...", plus the phrasings, synonyms, and file types).
  • It is the token contract - it alone decides when the expensive body loads. A precise description means the body loads exactly when useful and never otherwise.

Get the description right and the rest of the skill is easy. Get it wrong and the best body in the world never runs.

Part 2 · from a working skill to a published one

Phoebe's factories 6 min live

Once you can author a skill, two of Phoebe's own skills turn it into a repeatable pipeline. phoebe-skills-builder builds, sanitizes, and publishes showcase skills to GitHub; skill-build-partner is the data-skill factory that runs a fixed six-step pipeline end to end. Both exist so that "I built a skill" becomes "I ship skills on a line".

Livephoebe-skills-builder - build, sanitize, publish2 min▶

phoebe-skills-builder is the co-pilot for turning a private skill into a public showcase one. It brainstorms the idea, co-builds a clean public-ready skill, then sanitizes - the step that keeps client names, internal paths, and proprietary logic out of anything that goes public.

  • Build - shapes the skill with lots of questions, so the description and scope are sharp.
  • Sanitize - scrubs proprietary detail before publish. Non-negotiable for a public repo.
  • Publish - one skill at a time, with explicit approval, to the public showcase repo.
Publish deliberately Never bulk-publish. Each skill is a curated showcase piece, approved on its own. The public repo is a portfolio, not a dumping ground.
Liveskill-build-partner - the data-skill factory2 min▶

skill-build-partner is the specialist factory for data and applied-AI skills. It runs a fixed six-step pipeline and emits real executed artifacts - not just a SKILL.md but a runnable example that proves the skill works.

  • Designs the skill against a four-layer roadmap: infrastructure, data analytics, data science, gen AI.
  • Produces one of four artifact types - python plus charts, an ERD/DDL/contract, an HTML exec scorecard, or a runnable agent.
  • Publishes each as an installable skill plus a visual step-by-step page on the public data-skills site.
Real world

A "how to EDA with python" idea went through the six steps and came out as an installable skill with a real profiling run, saved charts, and a published walkthrough page. The pipeline made the artifact reproducible instead of a one-off notebook that rots.

Self-studyWhich factory for which job1 min read▶
  • A general workflow skill (a report format, a review checklist, a routing helper) - phoebe-skills-builder.
  • A data or applied-AI skill that needs a runnable artifact and a visual walkthrough - skill-build-partner.
  • Just scaffolding one skill fast, no publish pipeline - skill-creator from Part 1 is enough.
Part 3 · the payoff of the whole course

Write it token-lean 5 min live

This is where everything pays off. The whole course argued that the cheapest token is the one you never load - now you apply it to your own skill. The move is progressive disclosure: a thin SKILL.md holding just a name, a sharp description, and a short body, with all the heavy detail moved into reference files that load only when a step reaches for them.

LiveKeep the body under a screen2 min▶

The body is the part that loads every time the skill fires. If it's long, you pay for the long version on every use - even the steps that only need a fraction of it. So keep it short and point outward:

  • Body = the spine - the sequence of steps and the decisions, in plain instructions.
  • References = the flesh - the long tables, the edge cases, the templates, each in its own file the body names.
  • Load on demand - Claude reads a reference file only when a step it's on actually points there.
Real world

A skill's body held a 40-row lookup table it needed maybe one time in five. Moved to references/lookup.md, the body dropped to a screen and the table now loads only on the runs that use it. Four out of five invocations got cheaper for free.

LiveThe description is your token contract2 min▶

Come back to this one more time, because it's the payoff sentence of the whole course: a good description is the token contract. It's the one line that decides when the body - and everything the body pulls in - actually loads.

  • Too vague - the skill fires on unrelated tasks, loading its body when you don't want it. Wasted tokens.
  • Too narrow - it never fires, and the leverage you built sits unused. Wasted effort.
  • Just right - it fires exactly when useful, so the body's cost lands only where it earns its keep.
★ Try it nowHere is my skill's description: [paste it]. Test it against 3 tasks that should trigger it and 3 that shouldn't. Where does it misfire, and how would you tighten the wording?
Self-studyHow references get loaded1 min read▶

The body names its reference files by path - "for the full checklist see references/checklist.md". Claude follows that path only when it reaches the step that needs it. That's the same three-level progressive disclosure from Session 1, applied inside your own skill: name and description always, body when it fires, references only when a step reaches for them. Building your skill this way is not a nice-to-have - it's the difference between a skill that's cheap to keep installed and one that quietly taxes every session it touches.

Part 4 · the course in five habits

The token-budget playbook 3 min live

Five habits carry everything you've learned. Each one traces back to a session, so the whole course collapses into a checklist you can run on any task - not just when you're building a skill.

LiveFive habits, and where each was taught2 min▶

Run these in order on any real task. Together they are what "minimum token consumption" actually means in practice.

HabitWhat it meansTaught in
MeasureNotice what's filling your context before you optimizeSession 1 · context = budget
Don't loadProgressive disclosure - keep detail on disk until neededSession 1 + this session
OffloadSend heavy reading to a subagent with its own budgetSession 1 · OFFLOAD
CompressReturn conclusions, not raw dumps (caveman)Session 1 · COMPRESS
ReuseCache stable context - Projects + prompt cachingacross the course
The one habit that funds the rest Measure first. You can't offload or compress what you haven't noticed is expensive. Reading your own context as a budget is the reflex that makes every other move fire at the right moment.
Self-studyYour skill is where all five land1 min read▶

A well-built skill runs the whole playbook for you automatically. Its thin body doesn't load detail you don't need. It can dispatch a subagent to offload heavy work. Its output can be compressed. And installed once, it's reused across every project without re-explaining. That's why the capstone is building a skill: it's the playbook made permanent.

Demo 1 of 3

Scaffold a SKILL.md for a job you repeat ★ 6 min · follow along

Start from a job you actually keep re-explaining. Let skill-creator turn it into a real folder with a first-draft SKILL.md - the fastest way from idea to something you can run.

★ Scaffold promptUse skill-creator to scaffold a new skill for this recurring job: [describe it in one line - what you keep asking Claude to do]. Draft the name, the description, and a short body. Keep the body under a screen and tell me what depth you'd move into reference files.

Pick a job you've explained to Claude more than twice - a format, a checklist, a routine analysis.

Run the scaffold prompt. Read the draft description out loud - would a matching task contain those words?

Confirm the folder and SKILL.md exist. Notice how little is in the body so far.

Name the depth you'll move out of the body - that's Demo 3's job.

Demo 2 of 3

Tune the description until it triggers right ★ 7 min · build your own

The description is the trigger and the token contract. This demo is the eval: prove it fires on the right phrasing and stays quiet on the wrong phrasing.

Trigger-test promptHere is my skill's description: [paste it]. Run a trigger test: list 3 tasks that SHOULD fire this skill and 3 that should NOT. For each, say whether the current description would fire and why. Then propose a tightened description that gets all 6 right.

Paste your draft description into the trigger-test prompt.

Look for the misfires - a "should" that wouldn't fire, or a "shouldn't" that would.

Adopt the tightened description. Add the real phrasings and file types a matching task would use.

Re-run the test until all six land correctly. Now the description is doing its two jobs at once.

Real world

A skill for "decode a metric term into a carousel" wouldn't fire on "explain what churn rate means" - the description said "carousel" but not "explain" or "what does X mean". Adding those phrasings fixed it without touching the body. The trigger, not the instructions, was the bug.

Demo 3 of 3

Move the bulk into a reference file ★ 5 min · build your own

The payoff move: take the heavy detail out of the body and park it in a reference file, then watch the body stay cheap until a step actually needs the depth.

Thin-out promptMy skill's body has grown long. Move the heavy detail - the long tables, edge cases, and templates - into files under references/, and leave the body as a short spine that names those files by path. Show me the new body and confirm each reference loads only when its step is reached.

Identify what in the body is depth, not spine - anything you don't need on every run.

Run the thin-out prompt. The body should shrink to the sequence of steps plus paths to references.

Invoke the skill on a task that doesn't need the depth. Notice the reference file never loaded.

Invoke it on a task that does. Now the reference loads - on demand, exactly once, only when earned.

You just shipped a token-lean skill Thin body, sharp description, depth in references that load on demand. That's the whole course in one artifact you own - and it keeps paying every time the skill fires.
Homework

Try it yourself - ship one real skill ◐ 45-90 min total

  • Ship one real skill for a job you genuinely repeat. Working beats perfect - you can refine it later.
  • Give it a sharp description: pack in the phrasings and file types a matching task would contain, then trigger-test it on 3 should-fire and 3 should-not tasks.
  • Keep the body under a screen. If it's longer, you have depth that belongs in a reference file.
  • Put the depth in references/ and confirm each file loads only when its step is reached.
  • Run the five-move playbook once on a normal task - measure, don't-load, offload, compress, reuse - and note which move saved the most.
  • Leads: have each person ship one skill for a job their whole team repeats. A shared skill is training that installs once and pays forever.
  • Optional, for the certificate: the official courses below are free - this page covers their working content, but certificates come from Anthropic.
