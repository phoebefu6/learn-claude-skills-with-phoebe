Part 0

Why this session exists

Data work has a signature token trap: the raw data itself. Paste a million-row table to ask one question and you pay for every row. This session teaches the skills that keep data work lean and trustworthy - a pipeline from schema to contract to insight, a factory that turns any data workflow into a reusable skill, one accessible chart system, and profiling tools that summarize a dataset once so raw rows never fill your context. It's the practitioner layer for the data and ds tracks.

Part 1 · from a table you were handed to something you trust

Schema to insight 6 min live

The fastest way to a wrong answer is to query a table you don't understand. The schema-to-insights pipeline slows down for one step - turning a schema into an explicit data contract - and that contract is what makes every insight after it trustworthy.

Livephoebe-data-schema-to-insights - the pipeline3 min▶

The phoebe-data-schema-to-insights skill takes a schema and walks it to insight: it reads the structure, writes an explicit data contract, then produces offline insights against that contract - the biz-360-scan.

  • What it does - schema → data contract → offline insights, as one repeatable flow.
  • When to reach for it - the moment you're handed an unfamiliar dataset or asked "what's interesting in here".
  • Token effect - saves tokens. The contract is built once and reused; every later question references it instead of re-deriving the meaning of each column from raw rows.
★ Try it nowHere's a schema: [paste your CREATE TABLE statements or column list]. Use phoebe-data-schema-to-insights to write a data contract - meaning, rules, and owner per key field - then propose 3 offline insights I could pull from it. Don't query raw rows yet.
Real world

The "revenue" that wasn't. Two teams reported different revenue because one counted refunds and one didn't - the column was named the same. A data contract writes that rule down once, so the number means the same thing everywhere and nobody rebuilds the report after the mismatch surfaces.

Self-studyWhat belongs in a data contract2 min read▶
  • Meaning - what each field actually represents, in business terms, not just its type.
  • Rules - valid ranges, nullability, units, and the edge cases (does revenue include tax?).
  • Owner - who to ask when the rule is unclear or the data looks wrong.
  • Freshness - how current the data is and how often it updates.

A contract is the offline artifact that makes data self-serve. Written once, it stops every downstream analyst from re-guessing the same column - which is both a trust win and a token win.

Part 2 · turn a workflow into a reusable, showcased skill

The data-skill factory 6 min live

Any data workflow you repeat wants to be a skill. The factory designs and builds how-to-X-using-python skills across a four-layer roadmap, emitting real artifacts - and the public shelf is where the good ones live.

Liveskill-build-partner - the factory3 min▶

The skill-build-partner skill designs and builds how-to-X-using-python skills across the four-layer CDAIO roadmap: Infrastructure, Data Analytics, Data Science, and Gen AI. It runs a fixed pipeline and emits real, executed artifacts.

  • What it does - takes a data workflow and produces a runnable skill plus four artifact types: python + charts, an ERD / DDL / contract, an HTML exec scorecard, and a runnable agent.
  • When to reach for it - any data or DS workflow you've now done more than twice and want reusable and showcase-ready.
  • Token effect - saves tokens. The workflow is packaged once and loaded on demand, so you stop re-explaining the same EDA or forecasting recipe every session.
★ Try it nowI keep doing this data workflow: [describe it]. Use skill-build-partner to place it on the CDAIO ladder, then sketch the skill: what python + charts it emits, what the contract/DDL looks like, and what the exec scorecard would show.
Livephoebe-data-skills - the public shelf2 min▶

phoebe-data-skills is the public showcase repo where finished data skills live, each with a visual step-by-step page. The factory builds; the shelf publishes.

  • What it does - hosts installable data skills and their walkthrough pages as a curated data/AI showcase.
  • When to reach for it - when a skill is polished, de-identified, and worth showing to your audience or clients.
  • Token effect - reuse at the ecosystem level: a shared shelf means a team installs a skill instead of each person rebuilding it.
Real world

A forecasting recipe you built once becomes a page a colleague reads and a skill they install. The second person spends zero tokens rediscovering what the first already solved - reuse across people, not just across sessions.

Part 3 · one visual system + the right tool per job

See it right 6 min live

Data you can't see clearly is data you can't trust. One chart system keeps every visual on the same accessible footing, and a small set of data-infra tools each own a specific job - ERDs, catalog, profiling, quality.

Livedataviz - one accessible chart system3 min▶

The dataviz skill makes every chart read as one system: a form heuristic that picks the right chart type, accessible categorical and sequential palettes, and a validator that checks your colors before you ship.

  • What it does - chart-form heuristic + accessible palettes + a runnable color validator, in one visual system.
  • When to reach for it - before writing the first line of any chart, in any library or medium.
  • Token effect - prevents rework. Getting the encoding and palette right the first time avoids the "make it readable / fix the colors / now do dark mode" rebuild loop.
★ Try it nowI want to show [describe your data + the message]. Use dataviz: pick the chart form, choose an accessible palette, and run the palette validator before you render. Tell me why that form fits the message.
Livecore-workspace-skills - the data-infra tool how-tos2 min▶

core-workspace-skills carries the working how-to for the installed data-infra tools, so you use the right one per job instead of forcing everything through one:

ToolWhat it owns
DrawDBEntity-relationship diagrams from your schema
OpenMetadata + DataHubData catalog and lineage - what exists, where it came from
ydata-profilingAutomatic EDA - one profile report per dataset
Great ExpectationsData quality checks that fail loudly when data drifts

Each tool returns a summary artifact - a diagram, a catalog entry, a profile, a test result - not a raw data dump. That framing is what keeps the token bill low.

Part 4 · edit in place, keep the window lean

Work the notebook, keep context lean 4 min live

The final data move is the biggest token saver of the session: never stream raw rows when a summary will do. Edit notebook cells in place, turn sheets into visuals, and let a profiler compress a dataset once so a subagent can do the EDA and hand back only the profile.

LiveNotebookEdit - edit Jupyter cells in place2 min▶

NotebookEdit edits a specific Jupyter cell directly, rather than rewriting or reprinting the whole notebook into the conversation.

  • What it does - replaces, inserts, or deletes a single notebook cell in place.
  • When to reach for it - iterating on an analysis notebook cell by cell.
  • Token effect - saves tokens. You touch one cell instead of round-tripping the entire notebook through context on every edit.
Liveapp-script-partner - a Sheet into a visual tab2 min▶

app-script-partner turns a Google Sheet into a styled visual tab via a paste-and-run Apps Script - matrices, RAG status, roadmaps, scorecards - built in place.

  • What it does - reads a sheet's layout and writes an Apps Script that builds a clean styled tab from it.
  • When to reach for it - when a stakeholder lives in Sheets and you want a dashboard where their data already is.
  • Token effect - the script does the rendering inside Sheets, so the raw grid never has to live in your context to produce the visual.
The data token move, stated plainly Profiling tools summarize a dataset once. A subagent can run the EDA and return only the profile - so the raw rows do their work in the subagent's budget and never touch your main window. This is the single biggest lever in data work.
Demo 1 of 3

Schema to contract to insight ★ 6 min · follow along

Point the pipeline at a schema and watch it produce a data contract first, then an offline insight built on top of it - trust before answers.

★ The pipeline triggerUse phoebe-data-schema-to-insights on this schema: [paste it]. Step 1: write a data contract - for each key field give meaning, rules/units, and the owner to ask. Step 2: from that contract, propose one offline insight with the exact logic. Don't touch raw rows to build the contract.

Feed in a schema - CREATE TABLE statements or a column list is enough.

Read the contract critically: which column's meaning surprised you?

Check the proposed insight against the contract's rules - does it respect them (refunds, units, nulls)?

Save the contract - it's the reusable artifact every later query references.

Why this is a token move The contract is built once and reused. Every future question points at it instead of re-deriving each column's meaning from raw rows - reuse, not rework.
Demo 2 of 3

Profile a dataset so rows never fill context ★ 7 min · build your own

Feel the biggest data token move directly: instead of pasting a dataset, let a profiler summarize it once - ideally inside a subagent - and work from the profile.

Take a dataset you'd normally paste to explore. Notice how many rows that would be.

Run ydata-profiling on it to produce one profile report - distributions, missingness, correlations.

Add Great Expectations checks for the rules that matter (ranges, non-null keys). Let failures surface loudly.

Work from the profile and the check results. The raw rows never entered your main window.

Profile-not-dump promptDispatch a subagent to run ydata-profiling on [dataset] and set up Great Expectations checks for [the rules that matter]. Return only: the profile summary (distributions, missingness, top correlations) and which checks passed or failed. Keep the raw rows out of our main conversation.
Real world

A 2M-row export pasted to ask "is this clean?" can blow the whole window before you learn anything. One profile report - run by a subagent, returned as a summary - answers it in a fraction of the tokens, and the checks tell you exactly where it's dirty.

Demo 3 of 3

Build one accessible chart ★ 5 min · build your own

Go from data to a chart that reads as part of one system - right form, accessible palette, validated colors - before you render a single pixel.

State the message first: what should the reader conclude in five seconds?

Let dataviz pick the chart form from the message, not from habit.

Choose a categorical or sequential palette and run the validator - it flags colors that fail in light or dark.

Render, then check: legible, one meaning per color, works in both themes.

One-chart promptMessage: [what the reader should conclude]. Data: [describe it]. Use dataviz: pick the chart form and justify it, choose an accessible palette, and run the palette validator BEFORE rendering. Show me the validator result, then the chart.
Real world

A red/green status chart looks fine until a colorblind exec can't tell pass from fail. The palette validator catches that at design time - not after the chart is already in the board deck and needs rebuilding.

Homework

Try it yourself - this week ◐ 30-60 min total

  • Write a data contract for one table you use daily. Note which column's real meaning you'd have gotten wrong.
  • Profile one dataset with ydata-profiling instead of pasting it. Compare the tokens used to a raw-row exploration.
  • Add three Great Expectations checks to a pipeline you own and watch one of them catch bad data.
  • Rebuild one chart with dataviz - run the palette validator and confirm it works in both light and dark.
  • Take one repeated data workflow to skill-build-partner and place it on the CDAIO ladder.
  • Leads: have the team contract-document your five most-used tables. Shared meaning is the fastest data-quality win there is.
