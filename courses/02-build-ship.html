Part 1 · the discipline that stops rework before it starts

The build-loop skills 7 min live

Three superpowers skills form the spine of every build: write the failing test first, debug by root cause, then execute a written plan. They feel slower for thirty seconds and save you three rebuild rounds - which is exactly where the tokens hide.

Livetest-driven-development - write the failing test first2 min▶

The superpowers:test-driven-development skill enforces one order: test, then code. You describe the behavior you want, Claude writes a test that fails because the behavior doesn't exist yet, then writes only enough code to make it pass.

  • What it does - forces a failing test before a line of implementation, then codes to green, then refactors.
  • When to reach for it - any function or feature with a clear right answer. Bug fixes especially: the reproduction is your first failing test.
  • Token effect - saves tokens. A test pins the target so Claude builds the right thing once, instead of three rounds of "not quite - try again".
★ Try it nowUse test-driven development on this: [describe a small function]. Write the failing test FIRST, show me it fails, then write only enough code to pass. Do not write the implementation before the test.
Real world

The "almost right" trap. Asked cold for a date parser, Claude ships something that works on the examples and quietly breaks on leap years. Written test-first, the edge cases are tests before they're bugs - and you never pay the tokens to rebuild after a user finds them.

Livesystematic-debugging - root cause, not symptom2 min▶

superpowers:systematic-debugging stops the patch-and-pray loop. Instead of changing lines until the error goes away, it walks a fixed path: reproduce, isolate, find root cause, fix, verify.

  • What it does - a disciplined reproduce → isolate → root-cause → fix → verify sequence.
  • When to reach for it - any bug that isn't a one-second typo, and every bug that "came back".
  • Token effect - prevents rework. Symptom-patching creates new bugs and burns rounds; one root-cause fix ends the thread.
The tell of symptom-patching If the fix is "add a null check here" and nobody can say why the value was null, you patched a symptom. Systematic-debugging refuses to declare victory until the root cause is named.
Livewriting-plans then executing-plans2 min▶

For anything bigger than a single edit, the pair superpowers:writing-plans and superpowers:executing-plans separates thinking from doing. First you agree a written plan; then Claude executes it step by step without re-litigating the design mid-build.

  • writing-plans - turns a shaped idea into an ordered, checkable plan. Pairs with grilling and brainstorming from Session 1.
  • executing-plans - works the plan one step at a time, checking off as it goes, so a long build stays on rails.
  • Token effect - saves tokens. The plan is the shared source of truth, so the conversation stops re-explaining itself every turn.
Real world

A five-file refactor done conversationally drifts - by file three Claude has forgotten a decision from file one. Written as a plan first, each step carries its own definition of done, and a subagent can even execute steps in parallel.

Part 2 · one task, one branch, one clean context

Context isolation 5 min live

When two tasks share one working directory and one conversation, their context bleeds together - Claude confuses which change belongs to which goal, and your window fills with two problems at once. Worktrees fix this at the git level.

Liveusing-git-worktrees - a clean room per task3 min▶

superpowers:using-git-worktrees gives every task its own branch and its own checked-out directory. Task A and task B never touch the same files on disk, and each Claude session works one worktree, so the context stays about one problem.

  • What it does - creates a separate working directory per branch, so parallel tasks stay physically and mentally separate.
  • When to reach for it - any time you have more than one thing in flight, or a risky experiment you want quarantined from main.
  • Token effect - saves context. One clean context per task means Claude isn't paying to hold two unrelated problems in the same window, and it can't confuse them.
★ Try it nowSet up a git worktree for a new task called "fix-parser-bug" on its own branch, so this work stays isolated from my main branch. Explain what got created and how I switch back.
Real world

Reviewing a teammate's PR while mid-feature usually means stashing, switching, un-stashing - and a context now muddled with two goals. A worktree lets you open the PR in a second directory, review it in a fresh session, and leave your feature untouched.

Self-studyWorktrees vs branches vs stashing2 min read▶
  • Branch switch - one directory, one context. Fine for strictly sequential work.
  • Stash - a temporary shelf. Easy to forget, easy to lose, still one directory.
  • Worktree - a real second directory on its own branch. Parallel, isolated, and it survives a crash because it's on disk.

Rule of thumb: if two tasks would ever be "open at once" in your head, give each a worktree. The isolation is the point - for git and for Claude's context alike.

Part 3 · read and review without draining the window

Review + locate, compressed 6 min live

Understanding and reviewing code is where windows quietly drain - a vanilla search dumps whole files into your context. The caveman crew reads for you and returns compressed answers, and the superpowers review pair keeps quality high before you ship.

Livecavecrew-investigator - the read-only locator2 min▶

caveman:cavecrew-investigator is a read-only code locator. Ask it where something lives or how it's wired and it hands back a compressed file:line map instead of streaming whole files into your window.

  • What it does - finds and maps code, read-only, and reports in a compressed form.
  • When to reach for it - "where is this defined / what calls it / how does this flow work" across an unfamiliar codebase.
  • Token effect - saves tokens. Roughly 60% fewer than a vanilla search, because the raw files never land in your main context - only the map does.
★ Try it nowUse cavecrew-investigator to map where the function [name] is defined and everything that calls it. Return a file:line map only - do not paste the file contents into our chat.
Livecavecrew-reviewer & cavecrew-builder2 min▶
  • cavecrew-reviewer - reviews a diff and returns one line per finding, severity-tagged, no praise or padding. You scan issues in seconds, not paragraphs.
  • cavecrew-builder - makes surgical, 1-2 file edits with a tight context. It does not wander the whole repo; it changes exactly what you asked.

Token effect: both are terse-by-default, so a review or an edit costs a fraction of the tokens a chatty pass would. The reviewer's severity tags also let you triage - fix the reds, skip the nits.

Locator, reviewer, builder - a division of labor Investigator understands, reviewer judges, builder changes. Keeping them separate means each runs with the minimum context for its job, and you never pay a "read everything" tax just to make a two-line edit.
Liverequesting- & receiving-code-review, /review, /security-review2 min▶

The superpowers review pair and the built-in review skills raise quality before code leaves your hands:

  • superpowers:requesting-code-review - packages a change for review with the right context so the reviewer isn't guessing.
  • superpowers:receiving-code-review - turns feedback into fixes without ego, one item at a time.
  • /review - a general code-review pass over your changes for quality and simplification.
  • /security-review - a focused pass for security issues - injection, secrets, unsafe input handling.
Real world

A change that "works" can still leak a secret into logs. A quick /security-review before merge is far cheaper than the incident, the rotation, and the postmortem - the ultimate rework.

Part 4 · from working tree to live, then watch it work

Ship it 4 min live

Code that isn't shipped and seen running is a guess. The last mile is auditing and hardening a build, hosting it, launching the app to confirm the change, and treating docs and diagrams as code too.

Livebuild-deploy-html - audit, inline, harden, host2 min▶

The build-deploy-html skill takes a Claude-built HTML page and gets it truly shippable: it audits the markup, inlines assets so nothing 404s, hardens it, then hosts it on GitHub Pages or Netlify Drop.

  • What it does - audit + inline + harden Claude HTML, then publish to Pages or Netlify.
  • When to reach for it - any single-page site, course page, or dashboard you want live and durable.
  • Token effect - prevents rework. Catching a broken asset link at build time is far cheaper than debugging a live page that renders locally but breaks hosted.
Liverun - launch the app and see it work1 min▶

The run skill launches your project's app so you actually watch the change work, rather than trusting that it should. This is verification made physical - the difference between "the tests pass" and "I clicked the button and it did the thing".

  • What it does - finds how to launch this project (CLI, server, browser) and drives it to show the change live.
  • When to reach for it - after any change you could visually confirm - a UI tweak, a new endpoint, a fixed bug.
  • Token effect - prevents rework. Seeing it work closes the loop before an audience finds the gap you missed.
Self-studyThe docs layer - diagrams as code2 min read▶

The docs track ships text and diagrams the same disciplined way you ship code. Learn-markdown and learn-mermaid teach the formats; dataviz keeps any diagram or chart on one accessible visual system.

  • markdown - the lingua franca for READMEs, specs, and these very pages. Clean, diffable, reviewable.
  • mermaid - diagrams written as text, so a flowchart lives in the repo and updates in a PR like any other code.
  • dataviz - the form heuristic and accessible palettes that keep every diagram legible in light and dark.

Diagrams-as-code means your architecture picture never drifts from reality, because it's reviewed alongside the change that moved it.

Demo 1 of 3

Systematic-debugging on a real bug ★ 6 min · follow along

Take a bug you actually have and run the discipline: reproduce, isolate, root-cause, fix, verify. Watch how naming the root cause ends the thread instead of spawning the next symptom.

★ The debugging triggerUse systematic-debugging on this bug: [paste the error + what you were doing]. Walk the steps out loud: reproduce it, isolate where it starts, name the ROOT cause (not the symptom), propose the fix, then verify it's actually gone. Do not patch until you can tell me why it broke.

Reproduce it reliably - a bug you can't trigger on demand isn't fixed, it's hiding.

Isolate: narrow to the smallest input or code path that still breaks.

Name the root cause in one sentence. If you can't, you're still looking at a symptom.

Fix, then verify by re-running the reproduction. Green means done - not "the error message changed".

Why this is a token move Every symptom patch that misses spawns a new bug and another debugging round. One root-cause fix ends the whole chain - that's the rework you didn't pay for.
Demo 2 of 3

Spin a worktree for a parallel task ★ 6 min · build your own

Feel context isolation directly: start a second task in its own worktree while your first stays untouched, and notice the conversation stays about one thing at a time.

With a feature half-built, a "quick fix" request lands. Resist doing it in the same directory.

Use the prompt below to create a worktree for the fix on its own branch.

Work the fix in a fresh session - the context is only about the fix, not your feature.

Merge the fix, return to your feature worktree, and note nothing bled across.

Worktree isolation promptCreate a git worktree named "hotfix-login" on a new branch off main, in a separate directory, so it's isolated from my current feature work. Tell me the directory it created and the commands to switch between this and my main worktree. Then let's work the hotfix here with a clean context.
Real world

Three parallel builds, three worktrees, three clean contexts - a subagent can drive each. The main thread never holds all three problems at once, which is the same offload move from Session 1, applied to git.

Demo 3 of 3

Investigate, then edit surgically ★ 6 min · build your own

Run the crew as a relay: cavecrew-investigator maps where a function lives and what calls it, then cavecrew-builder makes the smallest edit that does the job - all without dumping the codebase into your window.

Pick a function you want to change but don't fully know the blast radius of.

Send cavecrew-investigator to map its definition and callers. You get a file:line map, not file dumps.

Hand that map to cavecrew-builder with the exact change. It edits 1-2 files surgically.

Run /review on the diff, then run to watch the change work.

Locate-then-edit promptStep 1: use cavecrew-investigator to map where [function] is defined and every caller. Return a file:line map only. Step 2: with that map, use cavecrew-builder to [the change], touching the fewest files possible. Then show me the diff for review before anything else.
Real world

Renaming a widely-used helper the naive way loads dozens of files and burns the window. Investigator returns the caller list, builder edits only those lines - roughly 60% fewer tokens, and no unrelated files touched.

Homework

Try it yourself - this week ◐ 30-60 min total

  • Fix one real bug with systematic-debugging. Write down the root cause in a single sentence before you touch the code.
  • Build one small function test-first. Confirm the test fails before you write any implementation.
  • Create a worktree for your next parallel task and work it in a separate session. Note whether the context stayed cleaner.
  • Run cavecrew-investigator on an unfamiliar part of your codebase and compare how many tokens it used versus a normal search.
  • Ship one page with build-deploy-html and then run it - watch the change actually work in the browser.
  • Leads: ask each engineer to bring one bug they fixed by symptom last month and re-diagnose the root cause. The gap is the lesson.
